<h1 id="getting-started">Getting Started</h1>

<h2 id="前提条件">Prerequisites</h2>

You need a Cloudflare account with the Workers Paid plan enabled.
Set `compatibility_date` to 2025-11-17 or later.
You must either specify `temporal` in `compatibility_flags` or set `compatibility_date` to 2026-12-01 or later.

```jsonc
{
  "compatibility_date": "2026-07-01",
  "compatibility_flags": ["temporal"]
}
```

<h2 id="インストール">Installation</h2>

```bash
pnpm create cloudflare@latest my-jobs --type=hello-world
cd my-jobs
pnpm add tsumugi
```

<h2 id="セットアップ">Setup</h2>

```bash
npx tsumugi init
```

When you run `init` in a new project, it creates the required Cloudflare resources and generates `wrangler.jsonc`, `src/index.ts`, `src/performers/`, and `.dev.vars`.
Finally, it applies the database migrations and exits.
If it fails partway through, it prints a warning along with the command to run again.

If a wrangler configuration file already exists, `init` does not rewrite it and instead prints the content you need to add.
In this case, the migrations are not applied either.
After you edit the configuration file, apply the migrations by following the printed steps.
The options and generated files are described in [CLI](/en/reference/cli).

The `TSUMUGI_METRICS` binding is optional.
If you do not set it, metrics are not recorded, but nothing else changes.
To use Flow and scheduled execution, set up additional bindings.
The details are in [wrangler bindings](/en/reference/config#wranglerのbinding), [Flow configuration](/en/guide/flow#設定), and [Schedule configuration](/en/guide/schedule#設定).

::callout{type="warning"}
After you update Tsumugi, apply the migrations again.
A new version may add migrations.
If unapplied migrations remain, the REST API responds with 503 and includes the names of the unapplied files in the response body.
::

<h2 id="performer">performer</h2>

You define job processing as a performer.
The `src/performers/hello.ts` file generated by `init` is the minimal example.
Rewrite the `perform` logic and the payload type to suit your use case.

```ts
// src/performers/hello.ts
import { Performer } from 'tsumugi/performer';

export class Hello extends Performer<{ name: string }, void, {}, Env> {
  async perform(payload: { name: string }): Promise<void> {
    console.log(`hello, ${payload.name}`);
  }
}
```

To add a performer, run `add-performer`.

```bash
npx tsumugi add-performer send-mail
```

This generates the performer file and appends one export line to `src/performers/index.ts`.

```ts
// src/performers/index.ts
export { Hello } from './hello.js';
export { SendMail } from './send-mail.js';
```

<h2 id="worker">Worker</h2>

`init` generates `src/index.ts` with the following content.
Export the performers from the Worker's entry point, and their names are used as binding names.
The rules for binding names are described in [binding names](/en/guide/performer#binding名).

```ts
import { bearerAuth, defineTsumugi } from 'tsumugi';
import { ui } from 'tsumugi/ui';
import * as performers from './performers/index.js';

export * from './performers/index.js';

const tsumugi = defineTsumugi({
  performers,
  // Get it from a secret; hard-coding it leaves it in the repository and the bundle
  auth: bearerAuth((env: Env) => env.TSUMUGI_TOKEN, { cookie: 'tsumugi_token' }),
  ui: ui({ tokenCookie: 'tsumugi_token' }),
});

// The Durable Object class must be re-exported
export { TsumugiJobShard } from 'tsumugi';

export default {
  ...tsumugi,
  async fetch(request, env, ctx) {
    const { pathname } = new URL(request.url);
    if (pathname === '/enqueue') {
      const id = await tsumugi.enqueue(env, { binding: 'Hello', payload: { name: 'world' } });
      return Response.json({ id });
    }
    // Pass everything else to the dashboard and the REST API
    return tsumugi.fetch!(request, env, ctx);
  },
} satisfies ExportedHandler<Env>;
```

The return value of `defineTsumugi` includes the `fetch`, `queue`, and `scheduled` handlers, as well as a function that enqueues jobs and a function that starts a Flow.
The full list of return values is in [Configuration](/en/reference/config#definetsumugi), and the differences between enqueue methods are in [Enqueueing jobs](/en/guide/enqueue#投入方法).

<h2 id="トークンの設定">Setting the token</h2>

If you do not specify `auth`, `tsumugi.fetch` responds to every request with 404.
The example above uses `bearerAuth`. In a local environment, it reads `TSUMUGI_TOKEN` defined in `.dev.vars`.
In production, run the following command to register the secret.

```bash
pnpm wrangler secret put TSUMUGI_TOKEN
```

<h2 id="動作確認">Verifying the setup</h2>

```bash
pnpm wrangler dev
```

When you access `/enqueue`, a Hello job is enqueued, and you receive a response of `{ "id": "..." }` containing the job ID.
The enqueued job appears in the list on the dashboard (`/`).
When you are prompted for a token, enter the value of `TSUMUGI_TOKEN` in `.dev.vars`.
Immediately after `init` generates it, the value is `dev-token`.
