# ADR-0048:ジョブごとのログを件数制限付きで保存しtraceparentを引き継ぐ

## 状況

試行履歴(ADR-0028)には開始時刻、終了時刻、例外が残るが、処理途中の記録は残らない
performerが終了せずSTALLEDになった場合、どこまで処理したかを詳細画面から確認できない
投入元のリクエストとジョブを関連付けるトレース情報も保持していない

## 決定

### ログ

`JobContext`に`log(message: string): Promise<void>`を追加する
各記録は`attempt`、`timestamp`、`message`を持ち、`timestamp`はDOが受け取った時刻のepochミリ秒とする

記録は呼び出し時にDOのSQLiteへ保存する
終了時までメモリに保持すると、performerが異常終了した場合に途中の記録を失うため現在の試行と一致する実行中のジョブのみを対象とし、古い試行や終了したジョブへの呼び出しは無視する

1ジョブあたり最新の20件を保持し、超過した古い記録を削除する
本文はJavaScriptの文字列長で2,000文字までとし、超過分を切り詰める
上限は試行ごとにリセットせず、手動リトライを含むジョブ全体で共有する

保存間隔の下限は1,000msとし、consumerとDOの両方で制限する
最初の呼び出しは即時に送信し、短い間隔の呼び出しは保存しない
送信待機の上限も1,000msとし、保存に失敗した場合は`console.error`へ出力してジョブの処理を継続する
利用者は`await ctx.log(message)`で保存処理の終了を待機

D1への反映は試行履歴と同じアウトボックスのスナップショットを利用する
ログを保存した時点でスナップショットを追加し、実行中も詳細画面から取得できるようにする
一覧にはログを含めず、詳細の`logs`に受信順で返す

ログはリトライでも保持する
DOの保持期間を過ぎたジョブはログとともに削除する
未反映のスナップショットはログを含むため、ジョブ削除後もD1への反映を継続できる
D1側は既存のジョブの保持設定に従う

### traceparent

直接のジョブ投入のオプションに`traceparent`を追加し、`JobContext.traceparent`へ渡す
未指定は`null`とする
W3C Trace Contextのversion `00`に対応する55文字の形式を受け付け、小文字の16進数以外や、全桁が0のtrace-id / parent-idは検証エラーとする

値はジョブに保存し、リトライでも同じ値を渡す
Tsumugiはspanを新規作成せず、投入時の文字列をそのまま引き継ぐ
外部のトレースSDKでspanを作る場合は、performerがこの値を親として利用する

RESTの`POST /api/jobs`では本文の`traceparent`を優先する
本文に無い場合は`traceparent`ヘッダーを利用し、採用した値が不正な場合は400を返す
対象は直接のジョブ投入であり、`tsumugi.start`やFlow内のノードへ自動で引き継ぐ契約は追加しない

## 帰結

詳細画面で、試行ごとの結果に加えて途中のログと投入元のトレース情報を確認できる
保存に成功したログはperformerの異常終了後も残るが、古い記録と短い間隔の呼び出しは保存されない
1ジョブで保持するログは本文40,000文字までとなり、DOの書き込み頻度とD1への反映量も制限できる
ログとtraceparentは認証済みの詳細APIで取得でき、D1への反映には遅延がある
