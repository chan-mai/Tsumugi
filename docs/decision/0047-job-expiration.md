# ADR-0047:ジョブの期限切れは投入直前と実行直前に判定しCANCELLEDへ集約する

## 状況

時刻の指定は`delayMs`と`runAt`だけで、期限を過ぎたジョブを実行しない指定が無い
一時停止やQueuesの滞留から復帰すると、SCHEDULEDのジョブがまとめて実行される
既に意味の無い通知や、古い入力に基づく同期処理もそのまま実行される
利用者はperformerの先頭で`createdAt`を確認して自分で判断するしかない

## 決定

投入時のオプションに`expiresAt`(絶対時刻)と`expiresInMs`(投入時刻からの相対)を追加する
両方の指定は`expiresAt`を優先する,`runAt`と`delayMs`の関係と同じ

期限切れは新しい状態を足さずCANCELLEDへ集約する
run期限がFAILEDと印で表した(ADR-0039)のと同じく、7状態(ADR-0012)を維持する
`expires_at`は読み取りモデルへ投影し、取り消しとの区別はこの列から可能

判定は2箇所で行う

- DOのtick: 実行可能になったSCHEDULEDが期限を過ぎていれば投入せずCANCELLEDへ
- consumer: 実行の直前に期限を判定し、実行せずDOへ報告する。Queuesで滞留したメッセージもここで対象になる

期限時刻での能動的な遷移は行わない
期限のためだけのalarmは書き込みを増やし、実行を止める目的には投入直前の判定で足りる

リトライのバックオフが期限を越える場合は、失敗報告の時点で予約せずCANCELLEDへ遷移する
期限まで実行できないことが確定した予約は、SCHEDULEDのまま残す意味が無い

遷移表にはQUEUED / RUNNINGからCANCELLEDへの遷移を追加する
利用はconsumerの実行直前の判定と、期限を越える再試行の中止に限定する
`cancel()`が受け付けるのは従来通りSCHEDULEDのみ(ADR-0012)

## 帰結

一時停止や滞留から復帰しても、期限を過ぎたジョブは実行されない
期限切れはCANCELLEDとして扱われ、失敗の通知(ADR-0043)の対象にならない
FAILED / STALLEDからの手動リトライも期限の対象になり、期限を過ぎていれば次のtickでCANCELLEDになる
at-least-onceの重複配送が期限をまたぐと、実行されたのにCANCELLEDと記録される場合がある
