# ADR-0043: 失敗の通知はジョブとして投入する

## 状況

ジョブがFAILEDやSTALLEDに達したことを記録するのはD1の読み取りモデルとAnalytics Engineだけで外部へ知らせる経路が無い(#30)
監視を組む利用者は、D1へ定期的にクエリを投げる仕組みを自分で用意することになる

## 決定

失敗を利用者が登録したperformerへジョブとして投入する, webhookのURLは持たない
ジョブにすれば投入も再試行も履歴も既存の仕組みがそのまま使え、通知の失敗を画面から追える

対象はFAILEDとSTALLEDに限る, 再試行で回復する途中の失敗は通知しない
回復する失敗まで届けると、通知の件数が障害の件数を大きく上回る

通知先はbindingを問わず1つ, 投入のたびに設定としてDOへ届ける
bindingごとに宛先を持たせると、新しいbindingを足すたびに設定漏れが起きる
投入の経路はworkerとRun DOとScheduler DOに分かれるため、どの経路からも同じ宛先を届ける
宛先を持たない経路から届いた設定では今の宛先を消さない, 消すとその後の失敗が捨てられる

積むのは投影と同じくアウトボックス(ADR-0008), 終端の捕捉と同じ場所で行う
投入が成功してからカーソルを進めるため、途中で落ちても次のtickで再送する

通知先のbinding自身の失敗は投入しない, 自分を呼び続ける循環になる
投入するジョブのIDは元のジョブと試行回数から決める, 再送しても同じIDなので二重にならない(ADR-0029)

## 帰結

失敗の知らせ方はperformerの中で決まる, SlackでもメールでもTsumugiは関知しない
通知先が落ちていれば通知ジョブがFAILEDとして残る, ただしその失敗は通知されない

宛先を設定する前に積まれた失敗は捨てる, 残すと設定した瞬間に古い失敗がまとめて届く
通知先は分割しない前提でshard 0へ投入する, 分けても順序も流量も変わらない
