# ADR-0045: concurrencyKey単位のレート制限を全キー一律のperKeyRateとして持つ

## 状況

ADR-0009の3軸のうちレート制限はshard全体に適用され、キー単位の流量は制限できない
`perKeyConcurrency`は同時実行の制御であり、実行が速いとキーあたりの単位時間の実行数は制限されない
テナントやアカウント単位に制限のある外部APIへ流量を合わせる手段が無い
partitionKeyでshardを分ければshard単位のrateで代用できるが、キーの数だけshardと設定が必要になる

## 決定

Policyへ`perKeyRate`を追加する, 全キー一律の1つの値としキーごとに異なる値は持たない
キーがnullのジョブには適用しない, `perKeyConcurrency`と同じ規則
shard全体の`rate`と併存し、両方を満たす時だけ投入する
キーのトークン不足は候補の除外にとどめる, 選考を停止すると他のキーとキーがnullのジョブまで投入されなくなる

キー別バケットは専用の表へキーごとに1行で持つ, 1行のJSONにまとめると行サイズがキー数の上限になる
tokensが上限の行は持たない, tickが読むのは投入候補のキーの行だけにし総行数がtickのコストへ影響しないようにする
tokensが0以上の行はrefilled_atからintervalMs以内に上限まで補充されるため、それより古い行は上限到達と同値として毎tick削除する
`perKeyRate`を無効にした後に残った行は次のtickでまとめて削除する

診断の`blocked`へ`perKeyTokens`を追加する, `perKey`(同時実行)とは緩和する設定が違う
alarmは除外したキーの最も早い回復時刻に設定する
全体の制約で選考を中断した後の未評価キーは次のtickで評価する, 全体の制約が解消されるまで投入は不可能なので、評価が次のtickになっても結果は変わらない
`ScheduleInput`の`keyBuckets`は省略可にする, 公開した`schedule()`を使う利用者のテストとの互換を保つ

## 帰結

投入を止める軸が4つになる, ADR-0009は3軸のまま残しここから参照する
`Policy`に`perKeyRate`が増えるので、独自にPolicyを構築している利用者は指定が必要になる(ADR-0042と同じ)
表の行数はアクティブなキー数に比例するが、tickのコストはキーの総数に依存しない
キーごとに異なる制限値が必要な場合はこの機構では表せない, bindingを分けて対応する
