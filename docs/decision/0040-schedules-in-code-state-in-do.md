# ADR-0040: 定期実行の定義はコードに置き状態を専用DOが持つ

## 状況

先の時刻を指定できるのは`delayMs`と`runAt`だけで、いずれも1回きり(#26)
定期実行が必要な場合はwranglerのcronトリガーから利用者が自分でenqueueすることになり、定義がTsumugiの外に出る
一覧も次回の実行時刻も表示できず、発火の消失の検知もできない

## 決定

`defineTsumugi`の`schedules`に名前と間隔と対象を登録する, 対象は単発のジョブとflowの両方を受ける
payloadとinputの写像関数を含む定義はコードのclosureに置き、状態は単一のScheduler DOがSQLiteに持つ(ADR-0030と同じ形)
次回の実行はDOのalarmで設定し、発火のたびに次の予定へ再設定する

間隔は固定間隔の`everyMs`とcron式のどちらかを受ける
cron式はUTCの分精度で解釈し、タイムゾーンの指定と`JAN`のような名前付きのフィールドは受け付けない
発火のIDはスケジュール名と予定時刻から決める, 二重発火は同じIDの再投入として既存の重複排除で無効になる(ADR-0021 / ADR-0029)
uniqueKeyは受け付けない, 予約は時間経過でしか解放されず2回目以降の発火が初回のジョブに統合される(ADR-0033と同根)

前回が終わっていない時刻に次回が来た場合の扱いは定義ごとに選ぶ, 既定は省略
省略の判定では前回のジョブとrunの状態をDOへ問い合わせる, 待つ選択肢は持たない

一覧はScheduler DOへ直接問い合わせる, D1への投影は持たない

## 帰結

定期実行の定義と次回の実行時刻がダッシュボードとREST APIから見える
`schedules`を使う構成ではScheduler DOのエクスポートとbindingが必要, 使わなければ設定の変更は不要

alarmの遅れで未消化になった予定は最も古い1回だけを発火し、残りは省略する
予定と実際の発火時刻を両方持つため、遅れは一覧の差として現れる

発火の失敗は理由を残して次回へ進める, 同じ回の再試行は続けない
進めずに再試行すると、恒久的に失敗するscheduleが先頭に残り続けて他のscheduleの発火を止める

DOのalarmは一度設定すれば継続するが、最初の1回は外から起動する必要がある
worker入口からisolateごとに1回だけ同期を送る, トラフィックの無い構成ではcronトリガーが起点になる
