# ADR-0040: 定期実行の定義はコードに置き状態を専用DOが持つ

## 状況

先の時刻を指定できるのは`delayMs`と`runAt`だけで, いずれも1回きり(#26)
定期実行が要る場合はwranglerのcronトリガーから利用者が自分でenqueueすることになり, 定義がTsumugiの外に出る
一覧も次回の実行時刻も出せず, 発火の消失にも気付けない

## 決定

`defineTsumugi`の`schedules`に名前と間隔と対象を登録する, 対象は単発のジョブとflowの両方を受ける
payloadとinputの写像関数を含む定義はコードのclosureに置き, 状態は単一のScheduler DOがSQLiteに持つ(ADR-0030と同じ形)
次回の実行はDOのalarmで仕込み, 発火のたびに次の予定へ張り直す

間隔は固定間隔の`everyMs`とUTCの分精度のcron式のどちらかで, 名前とタイムゾーンは持たない
発火のIDはスケジュール名と予定時刻から決める, 二重発火は同じIDの再投入として既存の重複排除に吸収される(ADR-0021 / ADR-0029)
uniqueKeyは受け付けない, 予約は時間経過でしか解放されないので2回目以降の発火が初回に吸収される(ADR-0033と同根)

前回が終わっていない時刻に次回が来た場合の扱いは定義ごとに選ぶ, 既定は飛ばす
飛ばす場合は前回のジョブとrunの状態をDOへ問い合わせる, 待つ選択肢は持たない

一覧はScheduler DOへ直接問い合わせる, D1への投影は持たない

## 帰結

定期実行の定義と次回の実行時刻がダッシュボードとREST APIから見える
`schedules`を使う構成ではScheduler DOのエクスポートとbindingが要る, 使わなければ設定の変更は不要

alarmが遅れて溜まった予定は最も古い1回だけを発火し, 残りは飛ばす
予定と実際の発火時刻を両方持つので, 遅れは一覧の差として現れる

DOのalarmは一度張れば自走するが, 最初の1回は外から起こす必要がある
worker入口からisolateごとに1回だけ同期を送る, トラフィックの無い構成ではcronトリガーが起点になる
